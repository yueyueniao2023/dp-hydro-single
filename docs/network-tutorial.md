# 干支流四库：连接关系驱动的精确联合动态规划

**教学合成数据，非真实电站资料。** 本例优先让初学者能运行、能手算、能找到每一段算法，而不是处理工程规模。运行：

```bash
mvn compile exec:java "-Dexec.mainClass=network.NetworkMain"
```

入口为 [NetworkMain](../src/main/java/network/NetworkMain.java)，核心为 [NetworkDp](../src/main/java/network/NetworkDp.java)，结果为 [24行CSV](../results/network/dispatch.csv)。

## 1. 水系、连接与外部来水

```text
干流：A ───→ B ───→ C ───→ 出口
             ↑
支流：D ─────┘
```

[RiverNetwork](../src/main/java/network/RiverNetwork.java) 中，Node包含编号、河流属性和Reservoir物理参数；Edge(from,to)表示连接；upstreamOf(id)给出直接上游集合：

| 库 | 直接上游 | 输入文件中的local来水 |
| --- | --- | --- |
| A | 空 | A库以上集水区的天然来水 |
| D | 空 | D库以上集水区的天然来水 |
| B | A、D | A、D以下至B之间新增集水区来水 |
| C | B | B以下至C之间新增集水区来水 |

`course=mainstem/tributary` 只用于说明。修改属性名称不会改变计算；修改 [connections.csv](../data/network/connections.csv) 会改变实际汇流，测试专门验证了这一点。

水系用Kahn算法拓扑排序：入度等于尚未计算的直接上游数；先取入度0的A、D，处理它们的出边后B才能入队，再处理C。若未能处理全部节点，说明有环，输入阶段立即报错。本模型允许汇流，但不支持分流；同一上游连接多个下游会报错，防止复制水量。

忽略传播时滞、河道损失和调蓄，本期平均流量关系为：

```text
I_A = q_A
I_D = q_D
I_B = q_B + R_A + R_D
I_C = q_C + R_B
```

只加直接上游。R_B已经包含流经B的水，C不能再加R_A和R_D。

## 2. 先估算规模，再选网格

每库只有3个离散水位，状态顺序固定为(A,B,C,D)，物理计算顺序是(A,D,B,C)。**两种顺序用途不同。**

联合状态数 S=3×3×3×3=81。6期朴素候选转移上界为：

```text
T × S² = 6 × 81² = 39,366 次联合转移
每次至多计算4库，共至多157,464次单库物理计算
value / previous 各为 (6+1)×81 = 567 个表项
```

实际会跳过不可达起点及不可行转移。一般N库、每库K个水位，状态数Kᴺ，枚举转移工作量约O(T×N×K²ᴺ)，DP与前驱表内存O(T×Kᴺ)。每库从3点增至5点，四库为625状态，6期有2,343,750候选转移；11点则有14,641状态、1,286,153,286候选转移。

这就是状态维数增加后计算量快速增长的原因。本教学入口在分配状态前拒绝过大网格/超过2000万候选转移，提示先减小规模；没有悄悄切换启发式算法。

## 4. 一条联合转移的物理计算

设期初为s=(zA,zB,zC,zD)，候选期末为s'，时长d天：

1. 从线性曲线取每库初末库容。
2. 按拓扑顺序取本库外部来水，加上已计算的直接上游总出库。
3. 对本库调用 [HydroPhysics.evaluate](../src/main/java/cascade/HydroPhysics.java)：

```text
Δt = d × 86400                             s
R = I + (V初 - V末) × 10^8 / Δt             m³/s
H = (Z初 + Z末)/2 - Z尾                      m，本例无额外水头损失
Q容量 = P装机 × 1000 / (9.81 × η × H)        m³/s，H>0
Q发电 = min(R, Q机组上限, Q容量)
Q弃水 = R - Q发电
P = 9.81 × η × Q发电 × H / 1000              MW
E = P × d × 24                              MWh
```

9.81η已经含水密度与kW单位换算：P(kW)=ρgηQH/1000，ρ=1000 kg/m³。公共Reservoir保存powerCoefficient=9.81η；输出MW再除1000，不能再重复乘效率。

水量平衡先唯一确定总出库R，再分配发电/弃水，不是先猜最大发电流量再把水量凑平。负泄流或超出下泄边界的转移返回null，直接淘汰；不修改R，不把负值截为0。水位越界同样不可行。公共模型中有正泄流却非正毛水头时不允许重力发电/泄流；本数据始终具有正水头。

四库阶段收益 G_t(s,s')=E_A+E_B+E_C+E_D。虽然同一股水可能多级发电，只要各电站落差不同，这不是电量重复计数；错误的是把同一股水在下游入流里加两遍。

### 简化假设

各期流量、功率均用平均值；库内水位用初末均值计算水头。尾水固定、效率固定，未模拟回水效应、水头相关机组特性、启停、生态瞬时流量、河道洪水演进。无蒸发、渗漏、时滞、河道损失或调蓄；无风、光、抽蓄、电池、电价、随机来水、负荷或电网约束。该优化目标是电量最大，不代表电力系统调度的完整目标。

## 5. DP递推、伪代码和Java对应

第t阶段状态表示已经运行t期时四库水位。F_t(s)表示所有到达s的可行历史中最大累计电量。

```text
F_0(s初) = 0
F_0(其他状态) = -∞

F_(t+1)(s') = max_{s且转移可行} [F_t(s) + G_t(s,s')]

最优值 = F_T(s目标末)
```

本模型下一期可行性与收益只依赖四库当前水位和已知来水，不需要更早历史。到达同一联合状态的较低收益历史可以丢掉，这就是DP能合并路径的依据。

```text
枚举四库水位的笛卡尔积，得到states
初始化value为-∞、previous为-1
value[0][initial] = 0

对每一期t：
    对每个可达的start状态：
        对每个end状态：
            operations = 空表
            按拓扑顺序逐库：
                I = 本库外部来水 + Σ直接上游operations[upstream].总出库
                计算本库初末水位对应的物理结果
                任一库不可行：放弃整个联合转移
            candidate = value[t][start] + 四库电量之和
            若candidate更大：
                更新value[t+1][end]
                previous[t+1][end] = start
    本期没有任何可达状态：报无解

只检查指定terminal，不在附近另选终点
若value[T][terminal]为-∞：报目标末状态不可达
从terminal逐期读previous，重算本期物理结果
反转回溯列表，得到正序调度过程
```

| 伪代码 | Java位置 |
| --- | --- |
| 水库与连接、直接上游、环检测 | RiverNetwork.Node / Edge / upstreamOf / 构造方法 |
| 四库水位状态 | NetworkDp.State(a,b,c,d) |
| 枚举81个状态与估算计算量 | NetworkDp构造方法 |
| 拓扑汇流及候选转移 | NetworkDp.evaluate |
| 单库物理公式 | HydroPhysics.evaluate |
| 四站收益求和 | NetworkDp.Stage.energyMwh |
| 最优值、前驱和递推 | NetworkDp.solve中的value、previous及三层循环 |
| 严格初末状态 | boundaryIndex、唯一初态赋0、指定terminal检查 |
| 回溯并重算物理结果 | solve末尾的逆序for循环 |
| 24行结果CSV | NetworkCsvWriter.write |

若两条路径电量相同，代码保留先遍历到的路径；可能存在多个最优调度。比较算法时先比较可行性和总值，不能仅凭水位路径不同判错。

## 6. 用实际输出手算第2期（包含上游弃水）

以下数值直接对应 [dispatch.csv](../results/network/dispatch.csv) 的第2期。时长1日=86400 s=24 h；本期选择的联合转移为：

`(200,140,90,180) → (200,141,90,182)`，顺序始终(A,B,C,D)。

按计算顺序A、D、B、C：

| 库 | 初→末水位m | 初→末库容亿m³ | 入流I m³/s | 总出库R m³/s | 水头H m |
| --- | --- | --- | ---: | ---: | ---: |
| A | 200→200 | 0.10→0.10 | 80 | 80 | 50 |
| D | 180→182 | 0.05→0.05864 | 45 | 35 | 31 |
| B | 140→141 | 0.08→0.08864 | 125 | 115 | 40.5 |
| C | 90→90 | 0.06→0.06 | 121 | 121 | 30 |

A库不蓄水，R_A=80。装机限制的流量为25000/(8.829×50)=56.631555 m³/s，小于机组上限60，所以发电56.631555、弃水23.368445，P_A=25 MW，E_A=600 MWh。

D增加库容0.00864亿m³=864000 m³，故R_D=45−864000/86400=35。发电流量受机组上限限制为30，弃水5，P_D=8.829×30×31/1000=8.21097 MW，E_D=197.06328 MWh。

B的来水为 **80+35+10=125**，包含A的23.368445和D的5 m³/s弃水。B也蓄水864000 m³，R_B=125−10=115。装机限制使Q发电=32000/(8.829×40.5)=89.491840，弃水25.508160，P_B=32 MW，E_B=768 MWh。

C的来水为 **115+6=121**，没有再加A或D。库容不变所以R_C=121，Q发电=25000/(8.829×30)=94.385925，弃水26.614075，P_C=25 MW，E_C=600 MWh。

本期总电量=600+197.06328+768+600=**2165.06328 MWh**。

全水系外部来水=80+45+10+6=141 m³/s，出口流量121；(141−121)×86400=1,728,000 m³，恰好等于B、D两库的蓄水增量之和。既可核查逐库水量，也可独立核查全流域守恒。

## 7. 为什么必须联合决策

给定A、D期初水位，它们各自的期末水位会分别决定R_A、R_D。B的入流含两者之和，所以B的可行转移和发电收益同时依赖A、D的决策。

单独优化A可能让其在高水头时多发，却把水集中排在D洪峰或B已满发的时段，增加B、C弃水；稍早腾库或把泄流移到别的时段，可能牺牲局部电量却提高全系统电量。先定各站的局部最优路径，会排除这些协调方案，所以通常不能保证全系统最优。这并不表示每一组数据都严格优于各库分别优化，只表示没有普遍最优保证。[双库测试](../src/test/java/cascade/CascadeDpTest.java)还给出了局部优化落后于联合优化的具体反例。

三个案例的变化：

| 内容 | 单库 | 双库 | 四库汇流 |
| --- | --- | --- | --- |
| 基本水位状态 | z | (z上,z下) | (zA,zB,zC,zD) |
| 额外历史状态 | 原案例有月内极差，需min/max | 无 | 无 |
| 候选转移的物理顺序 | 本库 | 上→下 | 按拓扑A、D、B、C |
| 来水 | 已知天然来水 | 上游决策+区间来水 | 所有直接上游决策之和+本库外部来水 |
| 阶段收益 | 一站 | 两站求和 | 四站求和 |
| DP本质 | 枚举、比较、存前驱、回溯 | 相同 | 相同 |

## 8. 输出、验证和练习

CSV每库每期一行，共6×4=24行，固定按A、B、C、D显示；显示顺序不等于计算顺序。包含期号、天数、水库编号、外部来水、初末水位与库容、总入流、总出库、发电流量、弃水、尾水、水头、MW、MWh、水量残差。库容单位是亿m³，不是m³；残差已经转成m³。

本次结果：A=2234.052480、B=3130.305504、C=2613.346320、D=719.598816 MWh，总计**8697.303120 MWh**；严格末水位为(201,141,91,181)。

[NetworkDpTest](../src/test/java/network/NetworkDpTest.java)核查逐库守恒、直接上下游含弃水汇流、全流域守恒、上下限、初末状态、总电量与CSV汇总、输入无环、连接实际参与计算，以及清楚的无解报错。另用每库2个水位、3期的小模型，独立枚举全部256条完整路径；不调用生产物理计算或DP递推，用另一套手写公式核对最优值。等时长、变时长两组均验证，详见[验证记录](validation.md)。

按“一次改一处、先预测再验证”练习：

1. 在数据副本把D装机降低，预测D弃水和B入流如何变化。总泄流由库容平衡决定，不能把D弃水从B来水中删掉。
2. 把B区间来水设为0，检查它仍收到A、D来水。
3. 把D→B改为D→C，预测B少掉哪部分水，再运行。
4. 添加C→A形成环，观察输入检查明确拒绝。
5. 把步长1改成0.5，先算5⁴=625个状态再运行；边界和物理模型保持一致，细网格包含粗网格时最优值应不下降。

未来加入水流时滞，需增加在途水等状态；加入风光储，则先定义负荷/功率平衡、储能状态和优化目标，再决定算法。不要在尚未掌握当前物理守恒时直接叠加复杂框架。
